# server-auth review

Scope: hst-server `internal/server/v1/oauth.go`, `pkg/oauth2/{oauth2,sessions,subscriber}.go`, `pkg/jwt/jwt.go`, `pkg/crypto/{argon2,token}.go`, `internal/middleware/*.go` (9 files), `internal/server/v1/trader/{auth,register,recover}.go`, `internal/server/v1/admin/auth.go`, `model/session.go`, `model/manager.go`, `utils/password.go`, `utils/fiber_locals.go`, `config/config.go`; plus callers read for the traces: `pkg/cache/cache.go`, `pkg/http/http.go`, `pkg/ws/hub.go`, `internal/server/server.go`, `internal/server/v1/{ws,routes,orders,account,journal_http}.go`, `admin/{routes,users,managers,groups,online,reference,journal}.go`, `trader/routes.go`, `utils/group_access.go`, `model/subjects.go`, migrations `sessions`, `password_reset`, `users`. 24 assigned files, 4311 lines; ~2500 more lines of callers. `go build ./...` clean.

## Summary
The core design is sound: argon2id with pepper + HMAC prehash, constant-time compare, dummy verify for unknown logins, EdDSA JWT with alg allowlist + kid, 256-bit opaque refresh tokens stored hashed, rotation with reuse detection, Redis-only `Protect`, sharded local cache with pub/sub invalidation, trusted-proxy IP handling, strict CORS and security headers. The three things that undo it: (1) every login writes the full `ViewToken` (access + refresh token) into `hst.journal.detail`, which the admin journal API returns to any manager with `right_srv_journals`; (2) revocation never deletes the refresh-token record, so logout, password change, rights change and admin disconnect all leave a working refresh token behind; (3) `ResetUserPassword` has no group-reach check and no session invalidation, so any manager holding `acc_manager` can take over any login including administrators. Rate limiting exists only for failed passwords; signup and recovery have none. Readability for a junior is good in oauth2/jwt/crypto/middleware, worse in `oauth.go` (900 lines, 120-line column list that duplicates `model.ManagerRightsColumns`).

## Readability notes for onboarding
- `internal/server/v1/oauth.go` — login/refresh/switch/logout/password in one 900-line file; flow is readable top to bottom, but `SelectManager` (120 lines of columns) and the mix of `denied()` vs direct responses cost time. Split `SelectManager` out and build it from `ManagerRightsColumns` first.
- `pkg/oauth2/sessions.go` — clear key layout and one function per operation; the gap between "revoke session" and "revoke refresh" is invisible to a reader, name it.
- `pkg/oauth2/oauth2.go`, `subscriber.go` — short, well commented; `PackManagerRights` map literal is fine.
- `pkg/jwt/jwt.go` — clear; remove the orphan comments.
- `pkg/crypto/argon2.go`, `token.go` — exemplary; nothing to simplify.
- `internal/middleware/*` — each file one job, each under 70 lines; good model for new middleware.
- `trader/register.go`, `trader/recover.go` — readable; `newResetCode` digit arithmetic could be `fmt.Sprintf("%06d", n)`.
- `trader/auth.go`, `admin/auth.go` — thin aliases to the shared handlers; swagger lives here, logic in `oauth.go`. Fine once you know.
- `model/session.go`, `model/manager.go` — enums and helpers clear; `Manager` methods and `ManagerRights` methods duplicate each other (`PermitsTerminal`, `CanDeal` ×2), say which one callers should use.
- `utils/password.go`, `utils/fiber_locals.go` — trivial and correct.
- `config/config.go` — long but linear; the auth block (`:365-382`) is easy to find. Hard-coded `MaxFailedAttempts`, `LockoutDuration`, `MaxFailedPerIP`, `RefreshAbsoluteTTL` should at least be named in the `.env` docs.

## Open questions
- Is the admin journal meant to be server-wide for `right_srv_journals`, or should it be masked by group like every other list? (Affects blast radius of F1 even after the fix.)
- Is "one session per trading account" (`oauth.go:164`) meant to also kill the other device's refresh token, or only its live socket? Today it does the latter.
- Should the per-login lockout exist at all, given it is a free denial-of-service against any known login number? MT5 locks per account too, so this may be intentional.
- Is `AUTH_PASSWORD_PEPPER` empty anywhere in production?
- Group rename with users present: intended to be blocked, or to cascade?
