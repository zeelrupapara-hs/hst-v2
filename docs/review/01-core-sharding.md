# core-sharding review

Scope: hst-core `internal/shardmap/shardmap.go`, `handler/shards.go`, `handler/nats.go`, `handler/handler.go`, `handler/load.go`, `handler/store.go`, `handler/publish.go`, `internal/book/book.go`, `internal/worker/worker.go`, `app/app.go`, `pkg/nats/nats.go`, `pkg/redis/redis.go`; hst-server `model/subjects.go`, `pkg/nats/nats.go`, `pkg/ws/{hub,client,ctx}.go`, `internal/server/v1/ws.go`; plus callers read for the traces (`handler/orders.go`, `dealing.go`, `accounts.go`, `query.go`, `ticks.go`, `positions.go`, hst-server `orders.go` publish/request, `model/event.go`). 21 files, ~4,460 lines. `go build ./...` and `go vet ./...` clean in hst-core.

## Summary
The ring, the hash and the forward-with-reply-intact design are sound and the subject strings match byte for byte on both sides. What is missing is any handoff protocol: each pod decides ownership from its own 5s view of Redis with no fencing, no generation number and no coordination with the pod on the other side of the move. Every join therefore opens a window (up to one refresh tick plus in-flight work) in which two pods both believe they own a shard, both answer commands and both write the account row, and every boot loads and then rewrites the entire accounts table from a snapshot taken seconds earlier. Queued worker jobs and the dealing queue are not released with the account, so a moved account can still be stopped out, re-priced or left with an orphaned dealer request on the old pod. Readability is good: the files are short, the comments say why, and a junior could follow the shard flow in an hour; the concurrency model (which lock guards `h.Shards`, `h.subs`) is the part that needs writing down.

## Flow traces

### A. Pod join/leave → reassign → flush/release/load → inbox open/close
1. Boot: `handler.Start` → `StartMarket` sets the all-shards map (load.go:49) and loads every account (load.go:52).
2. `Start` launches `WatchPodMembership` (handler.go:129) → `register` (shards.go:47) → `ReassignShards` (shards.go:89).
3. `livePods` `KEYS core:pods:*` (shards.go:67) → `shardmap.New` (shardmap.go:51) → diff (shards.go:131) → swap `h.Shards` (shards.go:104).
4. `CloseLostInboxes` (shards.go:220) → `ReleaseLostAccounts` flushes via `SaveAccount` (shards.go:173, store.go:214) and `Remove` (shards.go:176) → `LoadGainedAccounts` → `LoadAccountsIn` (load.go:454) → `OpenGainedInboxes` → `subscribeOwned` (nats.go:94).
5. Concurrently `Start` → `subscribe()` opens queue subs and owner inboxes from `h.Shards.Mine()` (nats.go:53-64).
6. Leave: `ctx.Done` → `unregister` (shards.go:55) or TTL expiry after 15s; peers notice on their next 5s tick.
Verdict: gap at step 2/4 (no handoff; gainer loads before loser flushes: #1), step 4 (flush of never-owned accounts: #2), step 3 (Redis failure → all shards: #3), step 5 (race with step 3/4: #5).

### B. api publish → queue → forward → owner → reply
1. hst-server `CreateOrder` → `s.publish(model.SubjectSystemOrders, e)` = `Publish`+`Flush`, 202 (orders.go:276,306-323); dealing/balance/positions/query use `request` with `engineTimeout` 10s (orders.go:326-339, live.go:27).
2. hst-core `QueueSubscribe("system.orders","engine_orders")` (nats.go:53,80-91) → `OrderSystemEventHandler` (nats.go:289).
3. `forwarded` → `PublishRequest("system.owner.<ShardOf(login)>.orders", msg.Reply, data)` (nats.go:114-115); subject built by the same `model.SubjectOwner` on the receiving side (model/subjects.go:163) and subscribed by `subscribeOwned` (nats.go:96). Subject/queue strings identical in both `model/subjects.go` copies (server :436-467, core :125-157).
4. Owner handles, `reply` → `msg.Respond` + `PublishRejected` (nats.go:351-362).
5. hst-server `request` decodes `TradeResult`.
Verdict: OK in steady state; gap at step 3 when no owner is subscribed (#7) and when two pods hold the inbox (#5) → two replies, first wins.

### C. In-flight command during a move
1. Pod A: `OrderSystemEventHandler` → `forwarded` false (A's map) → `NewOrder` gets entry (orders.go:19).
2. Pod A ticker: `ReassignShards` → `ReleaseLostAccounts` → `flushAccount` + `Remove` (shards.go:171-177) while step 1 is between `e.Unlock` and `save` (orders.go:388-410).
3. Pod B (already gained on its own tick) `LoadAccountsIn` reads DB before A's `save` commits.
4. A commits trade + `PublishTrade`; B's memory lacks the position; A's `reply` answers once (no duplicate reply), B never sees the order.
Verdict: gap at step 2/3 (#1, #4). Answered-once holds; nothing-lost does not.

### D. Account event fan-out to WS
1. Core `PublishAccount` → `PublishText("websocket.accounts.<login>.summary", X-Format text, X-Event)` and group copy (publish.go:132-136); trades via `PublishWS` with `X-Format json`/`X-Event` (publish.go:21-42).
2. hst-server trader socket subscribes `websocket.accounts.<login>.>` (ws.go:101, subjects.go:392); managers `websocket.groups.<family>.<path>` patterns (subjects.go:251-269) matching core `SubjectGroupScoped` (core subjects.go:72-113).
3. `eventFromMsg` reads `X-Format`/`X-Event` (event.go:35-39, ws.go:204-231) → `Client.Send` bounded egress, drop after 64 (client.go:104-125) → `writePump`.
4. Trader scrub of `group` (ws.go:188-202).
Verdict: OK. Header names and subject shapes match on both sides.

### E. Duplicate/lost work
- Duplicate: two owners during a join (#1), leaked inboxes (#5), stop-out/tick jobs on released entries (#4), EOD `Each` on both pods during overlap (#1).
- Lost: forward to an absent owner (#7), orphaned dealing requests (#6), account state flushed over by a booting pod (#2), worker queue full drops tick jobs silently (worker.go:57-61, logged only).

## Open questions
- Is one Redis DB shared by hst-server sessions and `core:pods:*`? (Decides how bad #9 is.)
- Is the deployment always a single pod today? Every P0 here only bites with ≥2 pods or a pod restart under load.
- Should the HTTP order path stay fire-and-forget (202) given the engine may drop a forward (#7), or move to `request` like positions/balance?
- `tempId` is per-pod negative counter (orders.go:605-611) and only keys the in-memory map until the row is written; uniqueness across pods is not needed unless tempIds are ever published — confirm `PublishTrade` is never called with a temp id (writeFill replaces it before publish: store.go:88-90, OK as read).
