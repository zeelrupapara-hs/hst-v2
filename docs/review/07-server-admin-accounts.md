# server-admin-accounts review

Scope: hst-server/internal/server/v1/admin (managers.go, clients.go, users.go, online.go, journal.go, server.go, routes.go, reference.go:ResetUserPassword), trader/ (trader.go, symbols.go, watchlists.go, alerts.go, policies.go, broker.go, routes.go, server.go), v1/ (account.go, alerts.go, navigation.go, journal_http.go, paging.go, oauth.go:SetPassword/RequirePasswordLength/SelectManager, orders.go:AccountInReach, ws.go:JournalEntry/NotifyClient), utils/*.go, model/{client,user,account,journal,manager}.go, middleware/authorization.go, pkg/oauth2/sessions.go:InvalidateLogin/RefreshLogin, migrations users/accounts/managers. 38 files, ~7,400 lines. `go vet ./...` clean.

## Summary
Read paths are well scoped: every by-id admin read goes through `AccountInReach`/`clientReach`, list queries carry the mask predicate, `sort_by` is allowlisted, all SQL is parameterised. The write paths are where it breaks: `ResetUserPassword` has no reach check and no session invalidation, `DeleteUser` cascades the money row and the manager row with no balance/position/last-admin guard, and `CreateUser`/`UpdateUser` accept any group, not only the caller's masks. Client PATCH has no validation at all. Trader self-scope (watchlists, alerts, symbols, journal) is correct: every query binds `snap.Login`. Journal audit consistently records actor (session login) and target in the message/detail. Readability is good for a junior except the two 85-parameter manager SQL blocks and the unmasked PII in WS/journal payloads, which a newcomer would not know to avoid.

## Flow traces

Engine subscribes `system.managers.>`. Verdict: OK, but gap: no `AccountInReach` on the login being promoted (can promote a login outside own masks).

**Update manager** — routes.go:52 → managers.go:516 reach → :534 body → :541 pack → :545 star → :549 `withinOwnScope` → :553 `wouldOrphanStar` → :559 `updateManager` → :569 `RefreshLogin` (rights rewritten in place; `OnRefresh` resubscribes WS) else `InvalidateLogin` → log → notify. Verdict: gap at step `withinOwnScope` (#5): target's existing rights not compared.

**Create client** — routes.go:32 (`ClientsCreate`) → clients.go:167 validate → :180 INSERT RETURNING → log actor/client_id → `NotifyClient` (groups of its logins: none → root) → `system.clients.created` → journal. Verdict: OK; gap #10 (creator can't read it back).

**Update client** — routes.go:34 (`ClientsEdit`) → clients.go:477 reach → :493 body (no validation, #6) → :501 COALESCE UPDATE → :583 reselect → notify/journal full record (#8) → masked response. Verdict: gap at validate and at notify.

**Create user** — routes.go:40 (`AccManager`) → users.go:101 validate → :111 `RequirePasswordLength` per slot → :121 `OpenLogin` (account.go:44: `OpeningBalance` group exists → hash → tx INSERT users + accounts → commit) → log actor/target → `NotifyUser` (WS group + trader profile, `system.accounts.created`, journal). Verdict: gap at step 3: no mask check on `Group` (#3).

**Update user (rights/group)** — users.go:236 reach → body → :265 `GroupExists` → :269 old group → :279 UPDATE → :301 `InvalidateLogin` when rights or group present → log → :313 `EventUserMoved` to old group → `NotifyUser`. Verdict: InvalidateLogin after commit OK; gap #4 (destination mask).

**Reset user password** — routes.go:44 (`AccManager`) → reference.go:324 → body validate → `RequirePasswordLength(login,"")` → hash → UPDATE by `login` → log → journal. Verdict: gap at step 1 (no reach) and after commit (no InvalidateLogin) (#1).

**Change own password** — admin/auth.go:84 & trader/auth.go:84 → oauth.go:617 `SetPassword` verify old → UPDATE (clears `reset_pass`) → :659 `InvalidateLogin`. Verdict: OK.

**Delete user** — users.go:332 reach → DELETE RETURNING group → `InvalidateLogin` (error only logged) → log → WS/NATS/journal. Verdict: gap (#2).

**IDOR on login params (trader)** — trader/routes.go: no trader route carries a `:login`; every handler binds `snap.Login` (trader.go:74,139; watchlists.go:60,245,282,386; alerts.go:121,150,247,287; journal_http.go:44; policies.go:71). Admin by-login routes all call `AccountInReach` except `ResetUserPassword`. Verdict: trader OK; admin gap #1.

**Trader self-scope on watchlists/alerts** — writes `WHERE watchlist_id=$1 AND login=$2` with `FOR UPDATE` (watchlists.go:385), symbol grant checked via `groups_symbols` (watchlists.go:358, alerts.go:87). Verdict: OK; `ReloadAlerts` per-pod (#7).

**Journal audit actor/target** — `JournalEntry` (ws.go:242) stores `login = snap.Login` (actor), ip, channel, os; target appears in the message (`journal.*Msg(target)`) and detail. `s.Log.Log` lines carry `actor`/`target` kv (managers.go:495, users.go:127, clients.go:203 uses `client_id`). Verdict: OK; detail payload carries PII (#8); `ResetUserPassword` logs `login` key not `target` (#1).

**Paging and filters** — `utils.QueryFilter` (query_filter.go:34): page≥1, limit 1..500 else 400, `sort_by` must be in the `Sortable` set, direction appended from a fixed string → interpolated into `ORDER BY` only after the allowlist; `search` always bound as `$1`; `GroupAccess` builds predicates from `$n` placeholders and a regex built by `maskRegex`/`regexQuote` from the caller's own stored masks, not request input. No injection surface found. `v1/paging.go` allows `limit=0` = unbounded (#12). `MyJournal` `from/to` via `QueryInt` (int, fine on 64-bit), `type` 0..12, `mode` enum checked, `channel` free text bound. Verdict: OK except #12.

**Rights bits on admin routes** — every mutating route in routes.go carries `Authorization(...)`; `Authorization` requires *all* listed bits (authorization.go:26). Mails `GET/attachments/:tracking_id/DELETE` (routes.go:179-183) are staff-only by design. Online uses `AccOnline` for disconnect (MT5 would also want `AccManager`; open question). Verdict: OK.

## Open questions
- Is `ResetUserPassword` intended to be admin-only (it is the only path to set a manager's password)? If so it needs `CfgManagers` for manager targets as well as the reach check.
- Should `DeleteUser` be a soft delete (MT5 keeps deleted accounts in the archive) rather than a cascade?
- Does hst-core tolerate `system.accounts.deleted` for a login with open positions, or does it keep trading the ghost account?
- Should `DisconnectSession` require `AccManager` in addition to `AccOnline`?
- Is PII in `hst.journal.detail` acceptable for the retention policy, given `MyJournal` exposes it to any `SrvJournals` holder via the `channel` filter?
